# ui-probe

描画されているアプリを実際に操作して、**対話が期待どおりに起きるか**を見る道具。

```bash
npm run probe                      # 全シナリオ
npm run probe -- --scenario=editing
npm run probe -- --show-logs       # main と renderer のログも流す
npm run probe -- --no-build        # ビルド済みのものを使う
```

期待と違うものがあれば終了コード 1。そのとき、そのシナリオの画面を
`ui-probe-<name>.png` に残す(git 管理外)。**DOM を読むだけでは分からないことが
ある** —— 要素は在るのに重なって読めない、色が背景と同化している。判定はしない。
見るのは人。

## なぜ必要か

型チェックもテストも通っているのに画面が壊れている、という状態が何度も起きた
(`CLAUDE.md` §3)。**そのうちいくつかは「何も起きない」という形でしか現れない。**

- 入力欄は出ているのに、フォーカスが移っておらず打鍵がどこにも入らない
- Project の枠が Task の前面に出ていて、中の Task に触れない

どちらも見た目は正常で、触ろうとして初めて分かる。ここでは Chrome DevTools
Protocol 経由で**本物のキーとマウスのイベントを送り、その後の DOM を読む**。

## これで分かること・分からないこと

**分かること**: 押した結果として何が起きたか。フォーカスの行き先、要素の増減、
どの要素が実際に手前にいるか。

**分からないこと**: 見やすいかどうか。配置の善し悪し。NFR-1 が言う可読性は
ここでは判定できない。**この道具はアプリを開いて使うことの代わりにはならない。**
一度直したものが黙って戻っていないかを確かめるためのもの。

## 仕組みと約束

- シナリオごとにアプリを起動し直す。前のシナリオの状態を引きずらないため。
- **`--user-data-dir` に使い捨てのディレクトリを必ず渡す。** DB の場所は
  `app.getPath('userData')` から決まるので、渡さないと利用者の実データを触る。
- **CDP のポートを決め打ちしない。** 固定番号だと、既にそれを使っている
  プロセス(開発中のアプリ、前回の残り)へ接続してしまう。こちらが起動した
  プロセスは listen に失敗しているのに、接続だけは先客へ成功する ——
  隔離した user-data-dir を素通りして、**本物のデータを書き換える。**
  `--remote-debugging-port=0` で OS に選ばせ、そのプロセス自身が標準エラーへ
  出したポートを読む。開いている URL も照合する。
- CI では動かしていない。画面が要るため。手元で走らせるもの。

## シナリオを足す

`scenarios/` に1ファイル置き、`scenarios/index.mjs` に足す。

```js
export default {
  name: 'editing',
  description: '一行で何を見るか',
  async run({ evaluate, waitFor, wait, key, type, drag, check }) {
    check('人が読んで意味が分かる文', 条件, 外れたときに見たい値);
  },
};
```

`wait(ms)` を並べるより `waitFor(ラベル, 式)` を使う。落ちたときに、
何を待っていたのかが残る。
