# Scope

This sprint investigates existing TODO apps (Todoist, Things 3, TickTick, Microsoft To Do, OmniFocus) and project-management tools (Jira, Linear, GitHub Projects) to understand: (1) the data model each assumes for a "unit of work," (2) the stated design rationale behind that model, and (3) documented user pain points and feature requests specifically around task dependencies and fine-grained, sequential implementation work (i.e., work below the granularity of a Jira ticket or GitHub issue). Sources prioritized: official docs, GitHub Issues/Discussions, Hacker News threads, and community forums (Reddit, GTD forums, Omni Group forums).

# Facts

**Personal TODO apps**

- Things 3's organizational model is a three-level hierarchy: **Areas** (general responsibilities, e.g. work/personal) → **Projects** (contained within areas) → **To-dos** (contained within projects, or created directly within an area). ([Things 3 review](https://medium.com/@smithtimmytim/review-things-3-for-mac-and-ios-114f4420f44b), [GTD forum thread on Things 3 project setup](https://forum.gettingthingsdone.com/threads/your-things-3-projects-setup.17174/))
- Things 3 is explicitly built around GTD-style daily planning — organizing a "Today" list rather than modeling cross-task ordering/dependency. ([Chad Landman, "Using Things 3"](https://www.chadl.co/blog/things3))
- In GTD (the methodology OmniFocus explicitly implements), a **project** is defined as "any desired result that requires more than one action step," and every active project must have a defined **next action**. GTD does not require the next action to be maximally granular — official guidance states "the next action does not always have to be super granular... if the next thing you need to do on a project is work on it for 3 hours, just put that." ([Inside OmniFocus: GTD](https://inside.omnifocus.com/gtd), [OmniGroup: GTD and OmniFocus PDF](https://downloads.omnigroup.com/software/MacOSX/Extras/OmniFocus/GTDandOmniFocus.pdf))
- OmniFocus/GTD organizes actions primarily by **tags/contexts** (tool, person, location, mindset, time needed) rather than by sequence or dependency — there is no single "next action list," but many tag-filtered views. ([Zapier: Complete Guide to OmniFocus](https://zapier.com/blog/getting-things-done-gtd-omnifocus/))
- Microsoft To Do does not support nested subtasks-within-subtasks (only one level of subtask/checklist item under a task), unlike Todoist. It also lacks sections/labels-based filtering comparable to Todoist. ([Todoist vs Microsoft To Do comparison, ClickUp](https://clickup.com/blog/todoist-vs-microsoft-to-do/), [SaaSHub comparison](https://www.saashub.com/compare-microsoft-to-do-vs-todoist))
- TickTick supports multi-level "subtasks" for breaking a task into smaller steps, but its free tier caps the number of tasks/subtasks and lists, and it caps priority levels at three (High/Medium/Low). ([TickTick Help Center: Multilevel Tasks](https://help.ticktick.com/articles/7055782219767349248))
- None of Todoist, Things 3, TickTick, Microsoft To Do, or OmniFocus natively support **cross-task dependency links** (i.e., "Task B cannot start until Task A is done") as a first-class relation — all rely on manual ordering, nesting, or tags as a proxy. (Inferred from absence of the feature across official docs cited above and corroborated by the HN/GitHub discussions below.)

**Project-management tools**

- Jira's canonical hierarchy is Epic → Story/Task → Subtask, a fixed, comparatively rigid model. ([Wikipedia: Jira (software)](https://en.wikipedia.org/wiki/Jira_(software)))
- Linear's sub-issue hierarchy has no documented depth limit in the current docs, but Linear's own design writing states projects were deliberately made "their own entity, with their own shape" rather than just a folder/label of issues or an issue-with-sub-issues, because the Linear team judged projects and issues to be conceptually different things. ([Linear: Design is more than code](https://linear.app/now/design-is-more-than-code))
- Linear explicitly positions sub-issues for work that is "too large to be a single issue but too small to be a project," i.e., a middle granularity tier between a project and a single issue. ([Linear Docs: Parent and sub-issues](https://linear.app/docs/parent-and-sub-issues))
- Linear supports optional, team-configurable automatic status rollup: parent auto-closes when all sub-issues are done, and/or sub-issues auto-close when the parent is marked done. Labels are not inherited from parent to sub-issue; team, priority, project, cycle, and (conditionally) assignee are. ([Linear Docs: Parent and sub-issues](https://linear.app/docs/parent-and-sub-issues))
- An open Linear GitHub issue (#1192, filed by a user, unresolved as tracked) requests that sub-issues be **visually connected to their parent directly on issue boards** — i.e., the hierarchy exists in the data model but is not always visually surfaced in the board view. ([linear/linear#1192](https://github.com/linear/linear/issues/1192))
- GitHub's "Tasklists" feature (predecessor to native sub-issues) went into private beta in January 2023 after a 2022 community discussion in which users explicitly asked for deeper hierarchy than the 1-level limit that existed at the time. ([community discussion #9913](https://github.com/orgs/community/discussions/9913))
- GitHub's blog post introducing native sub-issues states the goal was to let users "break down work into smaller, actionable steps" and to auto-roll-up parent-issue progress as children complete, "eliminating the need to manually check the status of all sub-issues," while trying not to add "unnecessary complexity" to the existing Issues UI. ([GitHub Blog: Introducing sub-issues](https://github.blog/engineering/architecture-optimization/introducing-sub-issues-enhancing-issue-management-on-github/))
- GitHub's separate **Issue Dependencies** feature (public preview as of the discussion cited) implements a "blocked by / blocking" relation, capped at 50 linked issues per direction, and is currently **not surfaced in Projects board columns/fields** — users report copying dependency state into a plain-text custom field via the API on a schedule as a workaround. There is no native dependency-graph visualization. ([community discussion #165749](https://github.com/orgs/community/discussions/165749))
- In GitHub's Issue Dependencies preview discussion, a user proposed that "blocked by" (their term for it) conflates two different relation types — strict Finish-to-Start blocking ("Task-2 cannot even begin until Task-1 is completed") versus a looser Finish-to-Finish relation — and requested the model distinguish them, alongside requests for "relates to," "duplicates," and "clones" relation types. ([community discussion #165749](https://github.com/orgs/community/discussions/165749))

**Cross-cutting: dependency requests across the category**

- On Hacker News (Jan 2023), a longtime paying Todoist customer wrote that despite nested projects, labels, and filters, Todoist "doesn't offer dependencies," which they considered "the big difference between something you can use on complex projects, and a 'mere' to-do list," and said they wanted a DAG (directed acyclic graph) representation for filtering/grouping. ([HN item 34470488](https://news.ycombinator.com/item?id=34470488))
- An earlier HN thread (2016) has a user stating they "haven't found a decent ToDo list with this killer feature: dependencies," wanting to mark a task as dependent on another being done, with time estimates and Gantt-style visualization. ([HN item 11352791](https://news.ycombinator.com/item?id=11352791))
- Another HN thread (2022) states plainly that "any todo list that doesn't account for dependency tasks is exclusively limited to" simple, unordered work. ([HN item 30885974](https://news.ycombinator.com/item?id=30885974))
- A 2020 HN thread about wanting "a simple kanban board with dependency graph, like Trello but with dependencies" references **Flying Logic** as a tool some users already use to build large manual dependency graphs, organizing tasks spatially so completed tasks sit "below" and blocked/future tasks sit "above." ([HN item 24208442](https://news.ycombinator.com/item?id=24208442))
- In Taskwarrior (CLI task manager), dependencies are modeled strictly at the **individual task level** — a maintainer states "projects are only hierarchy components, really just an attribute of a task, not things in and of themselves that can be depended on." Users wanting a task to depend on "all of project X" must either (a) script a mass-dependency creation, which goes stale if the project's task list changes, or (b) create a manual proxy "end of project" task that other tasks depend on. ([GothenburgBitFactory/taskwarrior discussion #2782](https://github.com/GothenburgBitFactory/taskwarrior/discussions/2782))
- In an open feature request on Super Productivity (an OSS personal task tracker), a user explicitly distinguishes the desired feature from subtasks: "There is no way to represent a connection between separate tasks (not the same as subtasks) from the same or different projects," proposing relation types (depends on / causes / relates to), a "Linked tasks" panel, and eventually a graph visualization comparable to Obsidian's graph view. ([johannesjo/super-productivity#2173](https://github.com/johannesjo/super-productivity/issues/2173))
- In an Obsidian Tasks plugin discussion, users requested the same underlying concept — dependency relations between discrete tasks distinct from nesting/indentation. ([obsidian-tasks-group/obsidian-tasks discussion #463](https://github.com/obsidian-tasks-group/obsidian-tasks/discussions/463))

# Findings

- Every tool surveyed organizes work as a **strict hierarchy or flat list** (Area→Project→Todo; Epic→Story→Subtask; Project→Sub-issue), not as a graph. Ordering/precedence between sibling or cross-branch items is not a modeled relationship in any of them by default.
- Where a "dependency" or "blocked by" relation does exist (GitHub Issue Dependencies, and third-party requests referencing Taskwarrior/Super Productivity/Obsidian Tasks), it is consistently a **separate, bolt-on relation** layered onto an already-hierarchical or flat base model — not integrated into the base data model, and in GitHub's case explicitly not yet surfaced in the primary board/table views.
- Multiple independent communities (GitHub Projects users, HN commenters across 2016/2020/2022/2023, Taskwarrior users, Super Productivity/Obsidian Tasks users) converge on the same unmet need — cross-task ordering/dependency distinct from parent-child nesting — described independently and using different terms ("dependencies," "blocking," "linked tasks," "DAG").
- Several tools/communities explicitly distinguish "nesting/hierarchy" (subtask-of) from "dependency/ordering" (blocked-by) as two different relations that get conflated in current UIs; requests to split them (e.g., Finish-to-Start vs. Finish-to-Finish in the GitHub thread) recur.
- GTD/OmniFocus's philosophy is notably different from the others: it deliberately avoids prescribing a specific granularity for a "next action," organizing instead by context/tag rather than by sequence — it is oriented around *what can I do right now given my current context*, not *what is the ordered chain of steps to completion*.
- No tool in this set was found (in the sources gathered so far) to visualize its data as an actual node-link graph for the end user; requests for graph-like visualization (Flying Logic, Obsidian's graph view, a "DAG for filtering/grouping") appear only as user wishes/workarounds, not as shipped features in Todoist/Things/TickTick/Microsoft To Do/OmniFocus/Jira/Linear/GitHub Projects.

# Open Questions

- None of the research so far captures how engineers actually use these tools (or don't) for the specific granularity described in the brief — sub-ticket, implementation-step-level work (write SQL → migration → Entity → Repository → Service → Controller). This sprint found general dependency/hierarchy complaints but not evidence specific to that exact granularity. Needs targeted follow-up (developer-focused subreddits, engineering blogs on personal task tracking during implementation).
- What does Jira's subtask model concretely look like in practice for engineers doing this kind of granular work, and what specific complaints exist? This sprint could not find primary-source (Reddit/HN/GitHub) discussion specific to Jira subtask granularity for implementation-level work — general Jira criticism found was not specific enough to cite as fact here.
- Are there existing OSS tools that *do* model tasks as an explicit dependency graph (not just "blocked by" as a bolt-on)? Flying Logic was mentioned as proprietary/commercial; worth investigating directly in a later sprint alongside the Visual Thinking tools (Heptabase, Logseq, tldraw) already scoped for R3.
- What exactly does GitHub's current sub-issue hierarchy depth limit allow (this sprint found conflicting/unverified signals — an old 1-level limit mentioned in a 2022 discussion, versus the newer sub-issues feature whose docs/blog post state no explicit limit)? Needs a primary-source check directly against current GitHub docs.
- How do teams currently combine a project-management tool (Jira/Linear/GitHub Projects) with a personal TODO app (Todoist/Things/OmniFocus) for the same underlying work — is there a documented pattern of "ticket in Jira, but I break it down further in my own personal tool," and if so, where does that breakdown get recorded/lost?
- Is there documented evidence (Reddit r/ExperiencedDevs, engineering blogs) of developers explicitly rejecting Jira/Linear-style ticket tracking as "too coarse" for day-to-day implementation sequencing, in their own words? This sprint's searches for that specific framing did not return citable primary sources and needs a different search strategy (e.g., searching Reddit directly rather than via general web search, or searching specific phrases developers use).
