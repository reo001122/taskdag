# Scope

This document covers Research Sprint 1: how engineers manage **granular, day-to-day implementation work** — the layer below Jira/Linear-issue-level tracking (e.g. write SQL → migration → fix Entity → fix Repository → fix Service → fix Controller). It looks at pre-implementation thinking/planning, task decomposition granularity, where TODOs are kept during implementation, individual vs. team differences, use of visualization, and reported pain points. Sources are primary where available (OSS repos, GitHub Discussions/Issues, Hacker News threads, developer blogs, one HCI research paper); generic "best tools" roundups were used only as leads, not as evidence.

# Facts

- On Hacker News, developers describe a wide range of concrete personal systems for tracking to-dos/progress, with no single dominant tool: plain text files, Obsidian, physical notebooks, org-mode, Todoist with tags, and Workflowy were all reported as actively used. ([HN #20101911](https://news.ycombinator.com/item?id=20101911))
- Some individual developers maintain a single tracking file *inside a git repository* (e.g. an org-mode file or a `backlog.md`) rather than in a separate app, so tasks move through explicit states like `todo → inprogress → done/postponed` in that file. ([HN #31146073](https://news.ycombinator.com/item?id=31146073))
- At least one reported personal system layers three list types on top of each other: day-level lists, sprint-level lists, and ticket-level lists linked back to Jira — i.e. the granular day-to-day layer is explicitly kept separate from, but linked to, the issue-tracker layer. ([HN #31146073](https://news.ycombinator.com/item?id=31146073), user "smoldesu")
- One reported system combines analog and digital tools simultaneously: pen-and-paper using a Today/Next/Someday (GTD-derived) structure for the granular daily layer, plus Trello only for brainstorming/longer-term storage, checked "a couple of times per week." ([HN #31146073](https://news.ycombinator.com/item?id=31146073), user "guiambros")
- A documented solo-developer system (blog, not a forum comment) explicitly separates "global ideas" (non-project brainstorming) from "project-specific" tasks tied to a repository, and further splits project tasks into: project overview (MVP goals), a running P-0/P-1 "laundry list," and a P-2 backlog — a three-tier decomposition below the ticket level. ([pankajpipada.com](https://pankajpipada.com/posts/2024-08-13-taskmgmt-2/))
- That same author explicitly moved away from a general note-taking app (MS OneNote) to a markdown+git system because switching to a separate app broke their flow state during implementation. ([pankajpipada.com](https://pankajpipada.com/posts/2024-08-13-taskmgmt-2/))
- That author also reports abandoning a dedicated "daily list" feature and a more structured note tool ("Foam Bubble") as unnecessary overhead, and reports that no system they tried successfully handled non-work (personal) tasks — i.e. self-reported tool churn and partial failure, not a settled solution. ([pankajpipada.com](https://pankajpipada.com/posts/2024-08-13-taskmgmt-2/))
- In-code TODO comments are treated by developers as a distinct mechanism from issue trackers: HN commenters describe TODOs as either (a) documentation of a known non-urgent issue, (b) something to be filed as an external issue, or (c) something to be fixed immediately before merging — three different fates for what looks like the same syntax. ([HN #44646801](https://news.ycombinator.com/item?id=44646801))
- Some developers explicitly avoid mixing actionable and non-actionable notes under one label, using distinct tags (e.g. `FIXME` vs `TODO` vs `NOTE`), reasoning that mixed severity causes people to become blind to the comments over time. ([HN #44646801](https://news.ycombinator.com/item?id=44646801), user "kstrauser")
- At least one commenter reasons that in-code TODOs and external ticketing systems serve different granularities on purpose: "tasks that should only ever be done if I touch this bit of code" belong in comments, while prioritized/scheduled work belongs in a ticketing system. ([HN #44646801](https://news.ycombinator.com/item?id=44646801), user "cortesoft")
- An existing OSS project (`archtechx/todo-system`) was built specifically because unstructured in-code TODOs "grow out of control" with no indication of priority or category, and proposes a numeric-priority + category tagging convention (`todo0`, `todo1`, `todo@testing`, etc.) layered directly on top of plain TODO comments. ([GitHub: archtechx/todo-system](https://github.com/archtechx/todo-system))
- In an OSS personal/team task-tracking tool (Super Productivity), a user requested a checklist/template feature specifically because routine multi-step tasks (they cite daily reporting-type routines) recur and are tedious to re-enter each time; the maintainer pointed to a pre-existing, still-open, unresolved request for the same underlying need (issue closed after 30 days of inactivity, unimplemented). ([GitHub Discussion super-productivity#1663](https://github.com/super-productivity/super-productivity/discussions/1663))
- GitHub's own product documentation frames its native "tasklists" (checklist-style sub-items inside one Markdown issue body) as a lightweight way to decompose an issue into smaller tracked steps, but GitHub is actively steering users toward a different feature ("sub-issues") as the intended replacement — indicating GitHub itself has iterated more than once on how to represent decomposition below the issue level. ([GitHub Docs: About tasklists](https://docs.github.com/en/enterprise-cloud@latest/get-started/writing-on-github/working-with-advanced-formatting/about-tasklists))
- An informal typology of developer "scratchpads" (personal experimentation/notes areas) proposes six recurring patterns observed among developers — no scratchpad, a full mirrored application, a console-only scratchpad, a class-library scratchpad, one evolving monolithic scratchpad, and an "arsenal" of many specialized scratchpads — and links the pattern used to how the developer decomposes problems (e.g., console/class-library patterns correlate with more modular thinking). This is one author's qualitative framework based on their own interviewing/hiring experience, not a controlled study. ([daedtech.com](https://daedtech.com/you-can-tell-a-lot-about-developers-from-their-scratchpads/))
- A peer-reviewed HCI study by Microsoft Research ("Let's Go to the Whiteboard: How and Why Software Developers Use Drawings," Cherubini et al.) empirically studied developers' use of drawings and found drawings are used both individually (personal planning/reflection) and collaboratively (team alignment/discussion), and that visual representation is treated as central — not incidental — to how developers plan implementation and reason about system/data-flow dependencies. *(Note: full text extraction from the archived PDF was degraded/compressed; findings above should be treated as directionally reliable but not verbatim-quoted — see Open Questions.)* ([Microsoft Research PDF](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/p557-cherubini.pdf))
- A 2026 essay by a Martin Fowler-affiliated author states, as a claimed professional norm rather than a measured finding, that experienced developers pairing on complex work "don't start at the keyboard," but first whiteboard components, data flow, and boundaries before writing code — and proposes this planning step is what current AI coding assistants skip. This is an opinion/argument piece, not empirical research. ([martinfowler.com](https://www.martinfowler.com/articles/reduce-friction-ai/design-first-collaboration.html))

# Evidence

- HN #20101911 direct examples: "DMell" — notebook w/ tasks crossed off + a "Goals/Brag sheet"; "Bender" — notebook, line-through completed, asterisk for important; "throwaway81523" — plain text file or org-mode, arguing elaborate systems create team friction; "smoldesu" — Obsidian with week/sprint/ticket list layers; "guiambros" — pen-and-paper GTD (Today/Next/Someday) + Trello, checked weekly; "BlameKaneda" — Todoist with tags (#CHAT, #RESEARCH, #BUY) plus a separate folder per larger project; "newusertoday" — single org-mode file in a git repo, `todo → inprogress → done/postponed`; "engineerDave" — Workflowy for 10+ years; "tiddles" — a "barely organised backlog.md" for side projects.
- HN #44646801 direct examples: "nevermore" — three legitimate fates for a TODO before merge (file an issue / fix now / demote to a plain comment); "pornel" — defends in-code TODOs because external trackers add triage overhead and lose local visibility; "p0nce" — uses semantic tags `FUTURE` and `PERF` distinct from generic `TODO`; "kstrauser" — warns that mixing actionable/non-actionable items under one tag makes developers "blind" to them over time; "muzani" — TODOs capture incomplete thinking (hardcoded values, O(n²) loops, temporary workarounds) without demanding immediate action; "cortesoft" — draws the line between "only if I touch this code" (comment) vs. prioritized work (ticket system).
- `archtechx/todo-system` README: motivation quote — in-code TODOs "often grow out of control (everything is just a 'TODO' with nothing indicating priority or category)"; proposed syntax includes `todo0`/`todo1`/`todo2` (priority-by-zero-count) and `todo@{category}` (e.g. `todo@responsivity`, `todo@testing`).
- `super-productivity` Discussion #1663: requester "Th3Link" — "Checklists are a great way to get through the same process over and over again like the daily routine with reporting back project times"; maintainer "johannesjo" pointed to a pre-existing duplicate issue (#1162) and asked users to upvote there instead; thread auto-closed after 30 days idle, unresolved.
- pankajpipada.com: direct quote — "Managing tasks through MS OneNote caused frequent context switches, often disrupting my flow state"; direct quote — "Markdown's minimalism is its strength"; explicit priority tiers named P-0/P-1/P-2/P-X; explicit statement that a "daily lists" feature was tried and abandoned, and that Git-based mobile editing felt "jittery and unreliable."
- GitHub Docs (tasklists): documentation explicitly frames tasklists as being superseded by "sub-issues," i.e., an evolution/iteration in how GitHub itself models sub-ticket decomposition.
- daedtech.com: names all six categories explicitly ("No Scratchpad," "Application Scratchpad," "Console-Based Scratchpad," "Class Library Scratchpad," "Monolithic Scratchpad," "Arsenal of Scratchpads") and proposes each as an interview signal of developer sophistication/decomposition ability — the author's own framework, presented without citing external data.
- Microsoft Research PDF: paper title and framing directly indicate empirical study of drawing use "before they change code" (design/refactor planning) and distinguish collaborative vs. solo use; granular quote-level extraction failed due to PDF compression — see Open Questions.
- martinfowler.com: direct quote — "When I pair program with a colleague on something complex, we don't start at the keyboard. We go to the whiteboard." Article proposes a 5-level abstraction sequence (Capabilities → Components → Interactions → Contracts → Implementation) as a way to reconstruct that whiteboard step for AI-assisted coding; this is a prescriptive proposal, not a study.

# Findings

Across independent sources, engineers do not appear to rely on Jira/Linear-level tickets to track the granular implementation layer; they layer a separate, lighter-weight mechanism *underneath* the ticket, and that mechanism varies widely by individual (plain text, notebooks, org-mode, Obsidian, Todoist, Workflowy, in-repo markdown files, in-code TODO comments). Several sources independently describe a multi-tier structure rather than a flat list: day/sprint/ticket layers (HN #31146073), or overview/laundry-list/backlog layers (pankajpipada.com), or priority-numbered/category-tagged in-code TODOs (archtechx/todo-system). Several sources also distinguish between granular notes that are "in-repo/in-code" (colocated with the work) versus notes kept in a general-purpose external app, with more than one source reporting that switching to an external app for this granular layer caused friction or broken flow state. In-code TODO comments are treated by multiple independent commenters as a distinct category from tracked issues — used for context-local, possibly-never-actioned notes rather than scheduled work — and at least one recurring failure mode is TODOs/comments losing meaning when actionable and non-actionable notes are not visually distinguished. Requests for checklist/template functionality inside existing personal task tools (Super Productivity) and GitHub's own iteration from "tasklists" to "sub-issues" both indicate that decomposition-below-the-ticket is a recognized but not fully solved feature gap in mainstream tools. On visualization, the one controlled empirical source found (Cherubini et al.) reports that developers do use drawings both individually and collaboratively as part of planning implementation and reasoning about dependencies/flow, though the specific quotes/findings could not be reliably extracted from the source PDF in this pass. One non-empirical opinion piece independently claims the same behavior (whiteboarding before coding) as a professional norm among experienced pairs, framed as something AI assistants currently skip.

# Open Questions

- The Microsoft Research PDF ("Let's Go to the Whiteboard") extraction was degraded (compressed/corrupted text layer); it should be re-fetched and read directly (e.g. via a proper PDF reader) to pull verbatim findings, sample size, and methodology before treating its claims as solid evidence.
- HN thread #10598766 ("Ask HN: How do you track issues, todos, features?") could not be fetched (rate-limited, HTTP 429) and has not yet been reviewed — likely contains more first-person examples and should be retried.
- No primary-source data was found yet specifically contrasting *team* granular-task practices vs. *individual* granular-task practices within the same organization (all evidence so far is either individual reports or requests aimed at individual/small-team tools like Super Productivity). This is a real gap — dedicated research into how granular implementation work is coordinated *across* a team (not just tracked by one person) is still needed.
- No evidence yet from GitHub Issues/Discussions on repos of dedicated visual/graph-based tools (e.g. tools explicitly built for dependency-graph task views) about why users adopted or abandoned graph-style views for implementation work — this connects to Research Sprint 3 and should be cross-checked there.
- No first-person accounts were found describing the exact chain named in the brief (SQL → migration → Entity → Repository → Service → Controller) — evidence so far is about granular implementation tracking in general, not this specific backend-layered-change pattern. Targeted search in framework-specific communities (e.g. Rails, Django, Spring/JPA, Laravel/Eloquent forums or issue trackers) discussing "how do you not lose track of all the files you touch for one DB change" may surface more directly relevant material.
- Reddit search via web search tools returned no directly attributable r/ExperiencedDevs or r/programming threads (search engine would not honor `site:reddit.com` filtering) — direct navigation on reddit.com or use of Reddit's own search/API would be needed to fill this source-priority tier as specified in the brief.
- It's unclear from current evidence whether developers who keep granular todos in-repo (org-mode/markdown/TODO comments) do so primarily to avoid context-switching (stated explicitly by pankajpipada and throwaway81523) or for other reasons (e.g. version-control/history benefits, searchability) — worth probing directly in follow-up research or in the human/AI brainstorming phase.
- The relationship between in-code TODO conventions (archtechx/todo-system, FIXME/TODO/NOTE tagging) and any *visual/graph* representation of those same tasks has not been explored — no source so far shows someone converting in-code TODOs into a visual dependency graph.
