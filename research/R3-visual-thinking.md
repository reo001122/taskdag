# Scope

This sprint investigates eight visual-thinking / canvas tools — Miro, tldraw, Excalidraw, FigJam, Obsidian Canvas, Heptabase, Workflowy, Logseq — to understand (a) their core interaction/data models (freeform canvas vs. outline vs. block-based vs. graph-based), (b) any documented design rationale from their makers, and (c) how real users/developers discuss using these tools for tracking work/tasks/dependencies specifically, as opposed to pure brainstorming or note-taking. No design conclusions or recommendations are drawn here.

# Facts

**Data models**

- Obsidian Canvas stores boards as `.canvas` files using the open **JSON Canvas** spec: a JSON document with a top-level `nodes[]` array (types: `text`, `file`, `link`, `group`, each with `id`, `type`, `x`, `y`, `width`, `height`) and a top-level `edges[]` array (each with `id`, `fromNode`, `toNode`, `fromSide`, `toSide`, optional `label`/`color`) — directed connections between nodes. ([obsidian.md/blog/json-canvas](https://obsidian.md/blog/json-canvas/), [jsoncanvas.org/spec/1.0](https://jsoncanvas.org/spec/1.0/), [DeepWiki: jsoncanvas format spec](https://deepwiki.com/obsidianmd/jsoncanvas/1.1-format-specification))
- JSON Canvas is explicitly an open, MIT-licensed format intended for interoperability across apps, and is plain JSON so files "diff cleanly in git" and can be tracked with history/blame/merge. ([obsidian.md/blog/json-canvas](https://obsidian.md/blog/json-canvas/))
- Logseq is a block-based outliner: the block is "the smallest addressable and thus linkable unit," blocks can have arbitrary sub-blocks, and each block is implicitly linked to its sub-blocks in a knowledge graph; pages are trees of blocks. It also ships a separate graphical "graph view" of bidirectional links, plus tasks/flashcards and whiteboards as additional features layered on the same block model. Newer ("DB") versions use a Datascript fork in-memory plus sqlite3.wasm for persistence. ([Logseq docs via chrislasar.github.io](https://chrislasar.github.io/logseq-doc/docs/explanation/blocks-and-pages/), [Logseq discuss forum](https://discuss.logseq.com/t/graphical-explanation-of-pages-blocks-and-references/15966), [logseq/docs db-version.md](https://github.com/logseq/docs/blob/master/db-version.md))
- Heptabase's model has three "fundamental elements": **Cards** (store knowledge/ideas), **Whiteboards** (spatial arrangement of cards to show structure of a topic), and AI Chat & Actions. A whiteboard is described as "an unlimited desktop for placing cards." ([Heptabase Public Wiki: Fundamental Elements](https://wiki.heptabase.com/fundamental-elements))
- Workflowy's model is a single, infinitely-nested bullet tree per user — one large tree spanning all of a user's content — where "folding" is replaced by "zooming" into a bullet and its children. The bullet is described as an intentionally style-agnostic atomic unit so users can repurpose it for arbitrary structures. ([molodtsov.me: The Evolution of Outliners](https://molodtsov.me/2020/07/outliners/), [Wikipedia: Workflowy](https://en.wikipedia.org/wiki/Workflowy))
- tldraw is an infinite-canvas SDK (not a single end-user app) with 13 built-in shape types and an explicit **bindings** system: an arrow's endpoints can bind to shapes so the arrow updates automatically when a bound shape moves; bindings are documented as generalizable to "constraint systems" and "visual programming environments," not just diagram arrows. tldraw renders shapes as a DOM tree rather than to an HTML `<canvas>`. ([tldraw.dev: default shapes](https://tldraw.dev/sdk-features/default-shapes), [tldraw.dev: arrow binding options](https://tldraw.dev/examples/arrow-binding-options), [HN #29264961](https://news.ycombinator.com/item?id=29264961))
- Excalidraw renders to an HTML `<canvas>` element (vs. tldraw's DOM approach) and is characterized by its hand-drawn sketch visual style; it is open source and has spawned separate self-hosted "platform" forks (e.g., a multi-canvas, cloud-storage-integrated fork) built by third parties on top of the core library. ([HN #29264961](https://news.ycombinator.com/item?id=29264961), [GitHub: BetterAndBetterII/excalidraw-full](https://github.com/BetterAndBetterII/excalidraw-full))
- FigJam's stated design intent centers on "playfulness and parity" for brainstorming meetings, explicitly positioned as a lighter-weight, easier-to-learn sibling of Figma design files, with native format interoperability into Figma design. Company material frames "play" as the governing design principle. ([Figma Blog: Introducing FigJam](https://www.figma.com/blog/introducing-figjam/), [Figma: Inside Figma — how our PM team uses FigJam](https://www.figma.com/blog/inside-figma-how-our-pm-team-uses-figjam/))
- Miro's v2 REST API models boards as collections of typed "items" (shapes, text, sticky notes, etc.) with a dedicated "connectors" (lines) resource added specifically to let developers programmatically link items on a board — i.e., dependency/relationship edges are a distinct, separately-versioned API concept from the nodes themselves. ([developers.miro.com](https://developers.miro.com/docs/rest-api-reference-guide), [Miro blog: REST API](https://miro.com/blog/rest-api/))

**Discourse on using these tools for task/dependency tracking specifically**

- On the Obsidian Forum, a user (RichieB) describes manually building a scrum-style board on Canvas using the community Tasks plugin, with separate cards for statuses (Available, In Progress, Complete, Blocked) and sprint cycles, and explicitly states the unsolved problem: *"I just don't know how to filter to only Tasks in the Current/Active Sprint without having to manually change each task or each code block every 2 weeks."* Responses proposed manual workarounds (date-range filter queries, tag variables, special status characters) — no built-in automatic/derived status mechanism existed at the time of the thread. ([Obsidian Forum thread #94221](https://forum.obsidian.md/t/manage-tasks-on-cards-on-a-canvas-according-to-scrum-sprint-and-status/94221))
- The Obsidian Tasks community plugin (separate from Canvas) has added a "task dependencies" feature letting users mark one task as depending on another to establish completion order — implemented as a plugin add-on rather than a native Canvas or core-app capability. ([Obsidian Ninja / Substack changelog summary](https://obsidianninja.substack.com/p/issue-3-task-dependencies-task-reminders))
- Multiple PKM-community sources (blog comparisons of Roam/Obsidian/Logseq) describe the built-in "graph view" (the node/edge visualization of backlinks) as visually appealing but of limited practical use for day-to-day work: graphs "only ever show links you typed by hand" and do not surface deeper/derived connections; one source states plainly that "the default graph view in all of these apps is unusable for day-to-day work and ideation." ([Medium: Comparing RoamResearch graph-view with Logseq and Obsidian](https://medium.com/alvistor/comparing-roamresearch-graph-view-with-logseq-and-obsidian-b0c1fd51c2ee), [Substack: A PKM Revelation — Obsidian Local Graphs](https://pjordan.substack.com/p/a-pkm-revelation-obsidian-local-graphs))
- GitHub's own issue tracker (not a canvas tool, but the nearest mainstream reference point for "derived blocked status") shipped native "blocked by / blocking" relationships between issues, and a "Blocked" indicator surfaces automatically on project boards/issue lists once a blocking link exists — i.e., a directly comparable derived-status mechanic already exists in a widely-used dev tool, arrived at via multi-year community request threads. ([GitHub Docs: creating issue dependencies](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/creating-issue-dependencies), [GitHub Changelog 2025-08-21](https://github.blog/changelog/2025-08-21-dependencies-on-issues/), [community discussion #165749](https://github.com/orgs/community/discussions/165749), [community discussion #11973 — original 2020-era request](https://github.com/orgs/community/discussions/11973))
- On Hacker News, users discuss tldraw/Excalidraw primarily in the context of quick diagramming/spec work and platform ergonomics (e.g., one user: *"for some quick spec work"*) rather than persistent task/dependency management; a maintainer (steveruizok) discusses iPad input-latency as a major technical constraint on adoption for that workflow. ([HN #45295286](https://news.ycombinator.com/item?id=45295286))
- tldraw's own GitHub repository shows heavy inbound interest as a foundation for other people's applications (feature requests like "tldraw as a complete application," #5155) rather than requests to natively support task/dependency semantics — no direct evidence was found of tldraw or Excalidraw issue trackers containing sustained discussion specifically about derived task-status/bottleneck features. ([tldraw/tldraw#5155](https://github.com/tldraw/tldraw/issues/5155))

# Findings

Across the eight tools, three distinct underlying data models recur: (1) freeform spatial canvas with explicit node+edge objects (Obsidian Canvas/JSON Canvas, Miro, tldraw, Excalidraw, FigJam, Heptabase's whiteboard layer), (2) hierarchical block/outline trees (Workflowy, Logseq's block model, Heptabase's card layer), and (3) a derived graph visualization layered on top of hand-authored links (Logseq/Obsidian/Roam "graph view"). Edges/connections are, in every canvas-model tool found, a first-class but purely representational object (a line with optional label/color) — none of the eight tools' own documentation describes edges as computing or driving a derived status (e.g., "blocked," "ready," "bottleneck") on the connected nodes. Where users have wanted status derived from structure (the Obsidian Canvas scrum-board case), it required manual, ad hoc workarounds via a third-party plugin, not a built-in capability. Separately, the PKM community's most direct real-world analogue to "deriving value from a graph" — the graph view in Obsidian/Logseq/Roam — is repeatedly described in user/blog commentary as visually engaging but not practically useful for daily work, and as limited to links the user typed by hand rather than anything computed. The one mainstream tool found to ship a true derived/automatic status from a dependency link is GitHub Issues' "blocked by/blocking" feature — which is not a visual-canvas tool at all, and which took a multi-year public request thread before being built.

# Open Questions

Should these be searched further (e.g., via podcast transcripts, conference talks, or archived early blog posts)?
- Is there a GitHub Discussions/Issues thread in tldraw, Excalidraw, or Logseq specifically requesting "derived status from graph structure" (e.g., "auto-mark node red if all its dependencies aren't done")? None was found in this pass — worth a more exhaustive issue-tracker search (including closed/older issues and non-English discussions).
- How do existing plugins that extend these tools toward task-tracking (e.g., Obsidian "Advanced Canvas," "Enhanced Canvas," the Tasks plugin, Logseq's task/query features) get used in practice — what do their own issue trackers reveal about unmet needs? Only surface-level plugin descriptions were captured here, not usage discussion.

Not investigated in this pass — flagged per the brief's source-priority list (papers were lowest priority and not reached).
- The Obsidian Canvas scrum-board thread and the graph-view criticism are the two clearest pieces of evidence found relevant to the product hypothesis, but both concern reading tools not originally built for this use case.
