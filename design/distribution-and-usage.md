# 配布と利用の流れ v1

ステータス: 初稿。OSSとして配布した場合の、エンドユーザーから見た導入・利用の流れを整理する。設計判断に跳ね返る論点を明示することが主目的。

## 1. 配布形態

### ビルド済みバイナリ(主経路)

GitHub Releases で配布する。

| OS | 形式 |
|---|---|
| macOS | `.dmg` |
| Windows | インストーラ(`.exe`) |
| Linux | `.AppImage` / `.deb` |

### ソースからのビルド

`git clone` → 依存インストール → ビルド、で動作すること。開発者・コントリビューター向け。

### コード署名

**macOS: 署名・公証を行う。** 開発者が Apple Developer Program に加入済みであるため、Gatekeeperの警告を回避できる。これは初回体験を大きく改善するので、リリース手順に組み込む。

- 署名 + 公証(notarization)をビルドパイプラインに組み込む
- CI(GitHub Actions)で行う場合、証明書とApple IDの認証情報をSecretsとして管理する必要がある
- **証明書やApple IDの認証情報をリポジトリに含めないこと**(OSSであるため特に注意)

**Windows: 当面は署名しない。** コード署名証明書は別途有償であり、必要性が生じてから検討する。SmartScreenの警告について、READMEに回避手順を記載する。

**Linux**: 署名の仕組みが異なり、AppImage等はそのまま実行できるため対応不要。

## 2. 日常の利用フロー

```
1. アプリ起動(ログイン時自動起動も可)
   → 単一キャンバスが表示される

2. 人間: キャンバス上で直接操作
   - Taskを作る / ドラッグして配置する
   - 依存エッジを引く
   - In Progress / Done を切り替える
   - childTaskを追加・並べ替える

3. AI(Claude Code等): 別ターミナルから会話しながら操作
   「今Readyなタスクは?」        → get_ready_tasks
   「認証まわりのタスクをDoneに」  → set_task_progress
   「このタスクもう要らないから消して」→ delete_task

   → いずれもキャンバスに即座に反映される
```

**このプロダクトの本命の使い方は「AIと会話しながら、隣でキャンバスが生きたビューとして更新され続ける」体験である。** 人間は全体像を目で把握し、細かい状態更新はAIに任せられる。

## 3. 初回セットアップ

1. アプリをインストールして起動する
2. AIから操作するために、MCPサーバーをAIツール側に登録する
   - アプリ内に接続情報(エンドポイント / トークン等)を表示する導線が必要
3. DBファイルの場所を確認できるようにする(`app.getPath('userData')` 配下)

**UI設計時の要件として、「接続情報とDBパスを確認できる画面」が必要になる。**

## 4. 未決定: MCPのトランスポート方式

**この構成では選択肢が実質的に絞られる。**

| 方式 | 適合性 |
|---|---|
| stdio | ✗ AIツール側がサーバープロセスを起動する方式。今回のMCPサーバーは「既に起動しているElectronアプリの中」にあるため噛み合わない(別途ブリッジプロセスが必要になる) |
| HTTP(ローカル) | ○ アプリがlocalhostで待ち受け、AIツールが接続する。起動済みのGUIアプリに後から繋ぐ用途に適合 |

HTTP方式を前提に、以下を Phase 4 の設計時に決定する。**実装時点で利用可能なMCPのトランスポート仕様を確認した上で確定すること。**

### セキュリティ上の考慮(流さないこと)

書き込み可能なAPIをローカルに公開することになるため、以下を検討する。

- **`127.0.0.1` へのバインド限定**(外部ネットワークから到達させない)。これは必須。
- **ただしそれだけでは不十分な可能性がある。** 同一マシン上の別プロセスや、ブラウザで開いた悪意あるページ(DNS rebinding 等)からエンドポイントに到達されうる。**トークンによる認証、および Origin ヘッダの検証を検討する。**
- ポート番号を固定にするか動的にするか(固定は設定が容易、動的は他アプリとの衝突を避けられる)。固定を既定とし、設定で変更可能にするのが妥当と思われる。

**この項目はセキュリティに直結するため、Phase 4 で「後で考える」としてはならない。**

## 5. 既知の制約: アプリ未起動時はAI操作ができない

MCPサーバーをElectronのmainプロセス内に置く構成のため、**アプリが起動していない間はAIからの操作を受け付けられない**。

- v1では許容する(外部レビューでも同様の結論)。
- 実際の利用では、キャンバスを開いたまま作業することが想定されるため、影響は小さいと考えられる。
- 独立プロセス化すれば解決するが、アーキテクチャの複雑さが大きく増すため、必要性が確認されてから検討する。

## 6. バックアップの運用

FR-9 の通り、ユーザーが任意のタイミングでDBファイルをエクスポートできる。

- 復元は、エクスポートしたファイルを元の位置に戻すことで行う
- 自動バックアップ・クラウド同期は行わない
- **README等で、定期的なエクスポートを推奨する記載が必要**(ローカル完結である以上、これがユーザー側の唯一の防衛手段であるため)
