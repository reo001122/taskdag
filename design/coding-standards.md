# コーディング規約 v1

ステータス: 初稿。実装中に随時参照・更新する生きたドキュメント。`design/tech-stack.md` の決定を前提とする。

## 基本方針

規約は「守らせるため」ではなく、**後から読んだときに意図が復元できること**と、**要件に書いた制約がコード上でも壊れないこと**を目的とする。特に後者(レイヤー境界)は本プロジェクト固有の重要な制約であり、最優先で守る。

## 1. レイヤー境界(最重要)

`design/tech-stack.md` のアーキテクチャ上の帰結より、以下は**規約ではなく要件由来の制約**である。

- **ドメインロジックは main プロセス側にのみ置く。** 循環検知、削除時の再接続、Ready/Blocked計算、Undo/Redoスタックの操作を、renderer(Reactコンポーネント)側に書いてはならない。
  - 理由: AI経由の操作(MCP)が renderer を通らないため。renderer に書いた瞬間、FR-7.5が破れる。
- **renderer は「表示」と「操作の発火」のみを担当する。** 状態の正しさを判断してはいけない。
  - 例: 「このエッジを繋ぐと循環するか」を renderer で判定してボタンを無効化するのは可。しかし**判定の実体は必ず main 側のドメイン関数を呼ぶ**こと。renderer 側で判定ロジックを再実装しない。
- **SQLiteへの書き込みは、ドメイン層を経由するもの以外に存在してはならない。** IPCハンドラやMCPツールから直接SQLを書かない。

**実装で判明した補足(Phase 2)**: ドメイン層は外部依存を持たない(`node:sqlite` すら import しない)ため、
**ドメインが db を呼ぶことはできない**。実際の配線は逆で、両者の上に立つ `app-service.ts` が
「ドメインの操作を実行し、生じた差分を db に書き出す」を担う。
したがって下図の `db/` は「domain から呼ばれる」のではなく「app-service から呼ばれる」が正しい。

ディレクトリ構成でこれを表現する:

```
src/
  main/
    domain/          ← ビジネスロジック。ここが唯一の真実。外部依存ゼロ
    db/              ← SQLiteアクセス。app-service からのみ呼ばれる
    app-service.ts   ← domain と db の配線。書き込みは必ずここを通る
    ipc/             ← rendererとの境界。app-service を呼ぶだけ
    mcp/             ← AIとの境界。app-service を呼ぶだけ
  renderer/
    components/  ← 表示のみ
    hooks/
  shared/        ← main/renderer両方が使う型定義のみ。ロジックは置かない
```

`ipc/` と `mcp/` は「薄い変換層」に留める。両者に同じロジックが書かれ始めたら、それは `domain/` に上げるべきサイン。

## 2. TypeScript

- `strict: true` を有効にする。`noUncheckedIndexedAccess` も有効にする。
- **`any` を禁止する。** 型が不明な場合は `unknown` を使い、絞り込んでから扱う。
- 型アサーション(`as`)は原則使わない。使う場合は、なぜ安全かをコメントで示す。
- ドメインの識別子は素の `string` ではなく branded type を使う。
  ```ts
  type TaskId = string & { readonly __brand: 'TaskId' };
  ```
  理由: TaskIdとProjectIdの取り違えのような、この種のアプリで起きやすいミスをコンパイル時に防げるため。
- 関数の戻り値型は、公開する関数には明示する(推論に任せない)。読み手が実装を追わずに済むため。

## 3. 命名

- 変数・関数: `camelCase` / 型・クラス: `PascalCase` / 定数: `UPPER_SNAKE_CASE`
- ファイル名: `kebab-case.ts`。Reactコンポーネントのみ `PascalCase.tsx`
- **要件で定義した用語は、コード上でも同じ語を使う。** `Task`, `childTask`, `Project`, `dependency edge`, `Ready`, `Blocked` など。
  - 独自の言い換え(`node`, `item`, `group`, `parent` 等)をドメイン層で使わない。要件とコードの対応が追えなくなるため。
  - ただしReact Flowのライブラリ境界では `node`/`edge` の語が出てくる。その変換は renderer 側に閉じる。
- 真偽値は `is` / `has` / `can` で始める(`isBlocked`, `hasChildTasks`, `canConnect`)。

## 4. 状態の扱い

- **軸a(Ready/Blocked)は永続化しない。** 常に依存エッジと軸bから導出する(FR-5)。DBにカラムとして持たせない。
  - 理由: 導出値を保存すると、更新漏れによる不整合が必ず発生する。
  - パフォーマンス上必要になった場合のみ、キャッシュとして持つことを検討する(その場合も「導出が正、キャッシュは従」を明確にする)。
- 軸b(Not Done/In Progress/Done)は永続化する。ユーザーの申告そのものであり、導出できないため。

## 5. エラー処理

- ドメイン層で「起こりうる失敗」(循環になる接続、存在しないTaskの参照等)は、例外ではなく **Result型で返す**。
  ```ts
  type Result<T, E> = { ok: true; value: T } | { ok: false; error: E };
  ```
  理由: 呼び出し側(IPC / MCP)が失敗を必ず処理することを型で強制でき、AIに返すエラーメッセージも組み立てやすいため。
- 「起こってはならない状態」(データ不整合など)は例外を投げる。握りつぶさない。
- **`Result` を返す関数の戻り値を読み捨てないこと。** IPC / MCP ハンドラが `Result` を無視すると、
  「失敗を必ず処理させる」という型の強制がその場で無効になる。失敗は呼び出し元(UI / AI)まで伝えること。
- **永続化に失敗したら、メモリ上の状態を DB に合わせて巻き戻す**(`app-service.ts`)。
  巻き戻さないと、DBに届かなかった変更がメモリ上に残り、それが次回以降の差分計算の基準になる。
  結果として失敗した変更は二度と再試行されず、再起動時に無言で消える。**DBを唯一の正とする。**

## 6. テスト

- **ドメイン層は単体テストを必須とする。** 特に以下は要件と1対1でテストを書く。
  - 循環検知(FR-3)
  - 削除時の再接続ルール 全パターン: 1-1 / 片側複数 / 両側複数 / 重複エッジ(FR-3)
  - Ready/Blocked の判定、特に入力エッジなし = Ready(FR-5)
  - Undo/Redo が削除+再接続を1単位として戻せること(FR-8)
- テスト名は要件番号を含める(例: `FR-3: 両側が複数の場合は自動再接続しない`)。要件との追跡可能性を保つため。
- **UI層に単体テストは書かない。** 「グラフが読みやすいか」はテストが答えられる問いではなく、書いても壊れやすいだけで守ってくれない。UI の正しさは手で確認する(CLAUDE.md §3)。

## 7. コメント

- **何をしているか**ではなく、**なぜそうしたか**を書く。コードを読めば分かることは書かない。
- 要件由来の判断には、対応する要件番号を書く。
  ```ts
  // FR-3: 入力・出力の両方が複数の場合は自動再接続しない
  ```
  理由: 後から「この分岐は消していいのか」を判断する際、要件に遡れるようにするため。

## 8. コミット

- Conventional Commits に従う: `feat:` / `fix:` / `refactor:` / `test:` / `docs:` / `chore:`
- 1コミット1論点。動く単位で刻む。
- OSSとして公開する前提のため、コミットメッセージは英語で書く。

## 9. ツール

- Lint/Format: **Biome**(`biome check --write`)。コミット前に自動実行する。
- 型チェックとLintは CI で必須にする(GitHub Actions)。
