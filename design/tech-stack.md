# 技術選定 v1

ステータス: 初稿。`vision/requirements.md` の要件を満たす技術構成を決定する。個別の設計(DBスキーマ、モジュール構成、API定義)は本ドキュメントのスコープ外とし、後続の設計ドキュメントで扱う。

## 決定サマリ

| 領域 | 採用 | 主な根拠 |
|---|---|---|
| 実行形態 | Electron | FR-7.5(常駐プロセスが必要)、ローカル完結、Cmd+Z等のネイティブなキーバインド |
| 言語 | TypeScript(全レイヤー) | フロント・バックエンド・MCPを1言語で統一。学習対象としても投資効率が高い |
| UI | React | グラフ描画ライブラリの選択肢が事実上Reactに集中しているため |
| グラフ描画 | React Flow (@xyflow/react) | 要件(ドラッグ接続・カスタムノード・接続時バリデーション)と機能が直接対応する |
| 自動レイアウト | ELK (elkjs) — 候補 | 依存グラフは階層的DAGであり、ELKのlayered algorithmが適合。要検証 |
| DB | SQLite (`node:sqlite`) | FR-7で決定済み。Node標準のため追加依存もネイティブ再ビルドも不要 |
| AI連携 | MCP TypeScript SDK | FR-7.5のアプリ層経由アクセスを実現する口として |
| ビルド | Vite + electron-vite | 開発時のHMRとビルドの標準的な組み合わせ |
| Lint/Format | Biome | ESLint+Prettierの代替。設定が単純で、個人OSSの維持コストが低い |
| テスト | Vitest(単体) + Playwright(E2E) | ドメインロジックの単体テストを主軸に置く |

## 各決定の根拠

### 実行形態: Electron

FR-7.5により、AIの書き込みを受け付けるアプリケーション層が常駐している必要がある。ブラウザだけで完結する構成は取れない。またFR-8のCmd+Z/Cmd+Shift+Zは、ブラウザ上ではブラウザ自身のショートカットと競合しうるため、デスクトップアプリの方が素直に実現できる。

Tauriと比較した場合、バイナリサイズと実行時のメモリではTauriが有利だが、バックエンドがRustになるため言語が2つになる。今回はMCPサーバー・ドメインロジック・UIを全てTypeScriptに寄せられる利点を優先した。

### グラフ描画: React Flow

要件との対応が直接的であることが決め手。

- FR-3「Taskの端をドラッグして矢印を伸ばし、接続先の端にドロップ」→ React Flowの Handle / Connection の標準機能
- FR-3「循環になる接続はドロップしても成立しない」→ `isValidConnection` フックで接続確定前に検証できる。要件をそのまま実装に落とせる
- FR-6「childTaskを内包するTaskノード」→ カスタムノードとして自由に描画できる
- ライセンスはMIT

**tldraw SDKを採用しなかった理由**: 自由形状のホワイトボードとしては強力だが、ノード+有向エッジという今回の用途にはオーバースペック。加えてライセンスがMITではなく、無償利用時にウォーターマーク表示の条件が付く形態のため、OSSとして配布する上で制約になりうる(採用検討する場合は最新のライセンス条項を要確認)。

**Cytoscape.jsを採用しなかった理由**: グラフ理論寄りの機能とレイアウトは強力だが、命令的なAPIでReactとの統合に手間がかかる。今回は「編集体験」が主役(Principle 1)であり、解析よりも編集操作の作りやすさを優先した。

### 自動レイアウト: ELK(要検証)

NFR-1で「可視化の可読性は主要な成功基準」としているが、React Flow自体は自動レイアウト機能を持たない。依存グラフは階層的なDAGであるため、ELKのlayered algorithmが構造的に適合する(dagreは開発が停滞気味であるため第2候補)。

**適用範囲は限定的**: FR-6の決定により、配置は手動が基本であり、自動レイアウトが走るのは**ユーザーが明示的に「整列」を実行したときのみ**。常時自動整列は行わない。したがってELKは「常に動く仕組み」ではなく「ボタンで呼ばれる一機能」として組み込む。この位置づけであれば、ライブラリの選定を誤っても差し替えコストは小さい。

### DB: `node:sqlite`(Node標準)

同期API(`DatabaseSync`)を持つため、Electronのmainプロセス内でトランザクション
(FR-3の削除+再接続)を素直に書ける。非同期ドライバのようにトランザクション境界が
コールバックで分断されない。

**当初は better-sqlite3 を選定していたが、Phase 2 の着手時に切り替えた。** 経緯:

- better-sqlite3 はネイティブモジュールであり、Electron の ABI 向けにビルドされる。
  そのため**素の Node(Vitest)から読み込めず、永続化層のテストが書けない**ことが判明した。
  Phase 0 では Electron 内でしか検証していなかったため顕在化していなかった。
- 一方 Electron 41 は **Node 24.15 を内蔵しており、`node:sqlite` が利用可能**であることを実測で確認した
  (SQLite 3.51.3、実験的警告の出力なし、同期API・トランザクション・PRAGMA いずれも動作)。

切り替えによって次の問題がまとめて消えた。

- ネイティブモジュールの再ビルド(`electron-builder install-app-deps`)が不要。`postinstall` も削除した
- Electron を更新するたびの再ビルド、CI での再ビルド手順も不要
- **テストが本番と同一の SQLite 実装で動く**

代償として **開発環境の Node を 22.5 以上(本プロジェクトは 24 に固定)にする必要がある**。
`.nvmrc` と `package.json` の `engines` で明示している。Electron 内蔵の Node と揃うため、
テストと本番の乖離もむしろ小さくなった。

### AI連携: MCP TypeScript SDK

FR-7.5で「書き込みはアプリケーション層経由」と決めたため、その口としてMCPサーバーをElectron mainプロセス内に持たせる。MCPの公式SDKはTypeScriptが主要な実装であり、言語統一の方針とも合致する。

参照系についても、FR-7.5の改訂により**MCPツールを正式な経路とする**(`get_ready_tasks` 等)。AIに生SQLを書かせるとスキーマ変更で壊れるため、安定したインターフェースを提供する。SQLiteへの直接SELECTは開発・デバッグ用の抜け道として残すのみ。

したがってMCPサーバーは、書き込み系(Task作成・削除・状態変更・エッジ接続)と参照系(Ready一覧・グラフ取得等)の双方を提供する。

### 副次的な利点: 書き込みが構造的に直列化される

MCPサーバーとドメイン層をmainプロセス内に置き、`node:sqlite` の同期APIを使う構成では、**UI経由の操作とAI経由の操作が同一のNode.jsイベントループ上で順次実行される**。したがって書き込みの競合は構造的に発生せず、明示的なロック機構を必要としない(FR-7.5)。

ただしこれは**データ整合性の話に限られる**。「ユーザーが操作中のノードをAIが削除する」といったUI側の問題は別途扱う必要がある。

## アーキテクチャ上の帰結(重要)

FR-7.5により、**UIからの操作とAIからの操作は、同一のドメインロジックを通らなければならない**。これは設計の骨格を決める制約である。

```
┌─────────────────────────────────────┐
│ Electron main process               │
│                                     │
│  ┌───────────────────────────────┐  │
│  │ Domain層                       │  │
│  │  ・循環検知                     │  │
│  │  ・削除時の再接続ルール          │  │
│  │  ・Ready/Blocked計算            │  │
│  │  ・Undo/Redoスタック            │  │
│  └───────────────────────────────┘  │
│         ▲              ▲            │
│         │              │            │
│    ┌────┴────┐   ┌─────┴──────┐     │
│    │ IPC     │   │ MCP Server │     │
│    └────▲────┘   └─────▲──────┘     │
│         │              │            │
│  ┌──────┴──────┐       │   SQLite   │
└──┤ renderer    │───────┼────────────┘
   │ React +     │       │
   │ React Flow  │       └── AI (書き込み)
   └─────────────┘
                     AI (SELECT) ──→ SQLite 直接
```

ドメインロジックをmainプロセス側に集約し、rendererとMCPサーバーの双方がそれを呼ぶ構造にする。**ドメインロジックをrenderer側(Reactコンポーネント内)に書いてはならない** — AI経由の操作がそれを迂回してしまうため。

## Phase 0 で判明した制約(実装時の注意)

### electron-vite 5 は Vite 8 に未対応 — Vite 7系に固定する

最新の Vite(8系)をそのまま導入すると、`@vitejs/plugin-react`(Vite 8を要求)と `electron-vite`(Vite ^5||^6||^7 を要求)の間で peer dependency が衝突しインストールに失敗する。

```
vite@^7.3.6
@vitejs/plugin-react@^5.2.0   ← 6系は Vite 8 必須なので使えない
electron-vite@^5.0.0
```

**electron-vite は Vite のメジャーバージョンに追随が遅れる。** Viteを上げる際は electron-vite の対応状況を先に確認すること。

### `type: "module"` を使わない(main/preload は CommonJS)

Electron は ESM に対応しているが、**preload スクリプトを ESM にすると `sandbox: false` が必要になる**。これはレンダラのサンドボックスを解除することを意味し、セキュリティ設定を弱める。

現状 `sandbox: true` + `contextIsolation: true` + `nodeIntegration: false` で動作しているため、この構成を維持する。renderer は Vite がバンドルするため、CommonJS 化の影響を受けない。

## 未決定事項(設計フェーズで詰める)

- Undoスタックの実装方式(コマンドパターンによる逆操作の保持 / スナップショット方式)。FR-8の「深さ」「粒度」「セッション跨ぎ」の決定と連動する。
- MCPサーバーの起動形態(Electron起動中のみ有効か、単独でも動くか)。アプリ未起動時にAIが操作できる必要があるかどうかで変わる。
- 状態管理ライブラリの要否(Zustand等)。React Flow自体が状態を持つため、追加が必要かは設計時に判断する。
