# 開発プロセス v1

ステータス: 初稿。`design/tech-stack.md` `design/coding-standards.md` を前提とする。

## テスト方針: レイヤーによって使い分ける

TDDを全体に一律適用はしない。**レイヤーごとに費用対効果が大きく異なる**ため。

| レイヤー | 方針 | 理由 |
|---|---|---|
| `main/domain/` | **テストファースト(TDD)** | 純粋関数でI/Oがなく、要件が既にケース列挙済み。テストが書きやすく、壊れたら即座に分かる |
| `main/db/` | テストを後から書く | SQLiteとの結合。スキーマが固まってからの方が効率的 |
| `main/ipc/` `main/mcp/` | 結合テストを後から | 薄い変換層。ドメインが正しければ大半は通る |
| `renderer/` | **TDDしない** | 「読みやすいか」はテストで判定できない。見て直す反復が必要 |

この境界は、FR-7.5由来のレイヤー境界と一致する。別々の理由で引いた線が一致していることは、構造が妥当であることの傍証。

### ドメイン層のTDD運用

要件のケースがそのままテストになる。実装前にテストを書く。

```ts
// FR-3: Task削除時の再接続ルール
describe('deleteTask', () => {
  it('FR-3: 入力1・出力1なら A→C に再接続する', ...)
  it('FR-3: 入力が複数・出力1なら 全入力→出力 に再接続する', ...)
  it('FR-3: 入力1・出力が複数なら 入力→全出力 に再接続する', ...)
  it('FR-3: 両側が複数なら再接続せずエッジを削除するのみ', ...)
  it('FR-3: 再接続先が既存エッジと重複する場合は重複を作らない', ...)
});
```

テスト名に要件番号を含める(コーディング規約 6項)。要件が変わったとき、影響を受けるテストを機械的に特定できる。

### UI層の進め方

テストファーストの代わりに、**動くものを早く見て判断する**。可視化品質が主要な成功基準(NFR-1)である以上、判断材料は動く画面そのものしかない。

E2Eテスト(Playwright)は、UIが安定してから**回帰防止目的でのみ**追加する。設計の駆動には使わない。

## 開発順序: ドメイン先行 + 早期の技術検証

### Phase 0: Walking Skeleton(技術検証)— ✅ 完了

**目的**: 技術スタックが実際に噛み合うことを最速で確認する。品質は問わない。使い捨ててよい。

| 検証項目 | 結果 |
|---|---|
| Electron + Vite + React が起動する | ✅ |
| SQLite が Electron main で動く | ✅ 当初は better-sqlite3 を再ビルドして解決。Phase 2 で `node:sqlite` に切り替え |
| WALモードが有効になる | ✅ `-wal` / `-shm` ファイルの生成を確認 |
| IPC で renderer ↔ main の往復ができる | ✅ 下記の方法で証明 |
| React Flow がノードを描画する | ✅ 同上 |

**検証方法(人手を介さない自動確認)**: renderer のマウント時に ping を送り、**その応答を待ってから2回目を送る**。DBのping件数が2になれば、以下が同時に証明される。

- App の描画が完走している(エフェクトは描画完了後に発火するため、React Flow の描画失敗なら発火しない)
- IPC の往路(renderer → preload → main → SQLite)
- IPC の復路(2回目は1回目が resolve しないと発火しないため)

目視確認に頼らず機械的に判定できる形にしたことで、検証が再現可能になっている。

判明した制約は `design/tech-stack.md` の「Phase 0 で判明した制約」を参照。

### Phase 1: ドメイン層(TDD、Electron非依存)

**目的**: プロダクトの正しさの核を、Electronを起動せずに完成させる。

- Task / childTask / 依存エッジ / Projectタグ のモデル定義
- 循環検知(FR-3)
- 削除時の再接続ルール(FR-3)
- Ready/Blocked の導出(FR-5)
- Undo/Redo のスタック(FR-8)

**このフェーズのコードは Electron・SQLite・React に一切依存させない。** 純粋なTypeScriptとして書き、Vitestだけでテストする。

利点:
- テストが高速に回る(Electron起動が不要)
- 依存がないため、後から実行形態を変えたくなっても影響を受けない
- ロジックの正しさとフレームワークの都合が混ざらない

### Phase 2: 永続化 — ✅ 完了

- SQLiteスキーマとマイグレーション(`PRAGMA user_version`)
- ドメインモデル ↔ DB 行のマッピング(`db/rows.ts`)
- 差分計算と差分適用(`db/diff.ts` / `db/repository.ts`)。トランザクション内で実行
- ドメイン層と永続化層の配線(`app-service.ts`)
- ドメイン層との結合テスト

**着手時に技術選定が変わった**: better-sqlite3 が Electron ABI 向けにビルドされるため
素の Node(Vitest)から読めず、永続化層のテストが書けないことが判明した。
Electron 41 が内蔵する Node 24 で `node:sqlite` が使えることを実測で確認し、切り替えた。
経緯は `design/tech-stack.md` を参照。

**検証したこと**:
- 差分計算(純粋関数)— childTask の並べ替えが `order_index` の更新として現れること等
- 往復(保存 → 読み戻しで一致)、DB制約による不変条件の担保、トランザクションのロールバック
- **SQLビューとドメイン関数の一致** — `task_readiness` は `domain/readiness.ts` の二重実装に
  あたるため、同じケースを両方に通して結果が一致することを確認している
- Electron 上での実地確認: 起動 → Task作成 → 終了 → 再起動でデータが残ること

### Phase 3: UI — 実装済み(視覚的な作り込みは継続)

- React Flow によるキャンバス、カスタムノード(childTask を内包する Task)
- ドラッグによる接続と循環防止、削除確認(FR-1)、折りたたみ、整列(FR-6)
- 完了の減光と非表示トグル(FR-6)、Project の枠、Cmd+Z / Cmd+Shift+Z(FR-8)
- IPC の配線と**境界での実行時検証**

**IPC はコマンド1本の判別可能ユニオンにまとめた。** 操作ごとにチャンネルを増やすより
境界が1箇所で済み、Phase 4 の MCP ツールもほぼ同じ形を再利用できる。
実行時検証(`ipc/validate.ts`)もここに集約している —— 型は実行時に存在しないため、
renderer や AI から届くペイロードを止める関門はここしかない。

**`isValidConnection` が同期APIである問題**: 循環判定はドメイン層にあり IPC 越し(非同期)になる。
renderer で到達可能性を再計算するとドメインロジックの二重実装になるため、
接続ドラッグの開始時に「接続可能な相手の一覧」を一度だけ取得し、以降は同期的に照合する。
判定の実体はドメイン層のまま。

ここから視覚的な反復が始まる。**このフェーズで初めて「本当に見やすいか」が判断できる**ため、要件の見直しが発生する可能性がある。

### Phase 4: MCP

- ドメイン層をMCPツールとして公開
- Phase 1〜2 が完成していれば、薄い変換層を書くだけで済むはず

**Phase 3 より後に置く理由**: 人間が使えないものをAIに操作させても検証しづらいため。ただしPhase 1完了時点で、CLIから叩いて動作確認することは可能。

## Git運用

- **`main` へ直接コミットしない。** 変更は feature ブランチで行い、**動作確認を経てから** main へマージする。
  - 画面に関わる変更は、実装した側では正しさを確認しきれない。型チェックもテストも通るのに
    見た目が壊れている、という状態が実際に何度も起きた。人の目を通す段階を挟む。
  - ブランチ名は `feature/<何を変えるか>`。
- コミット: Conventional Commits(コーディング規約 8項)。
- **Phase 0 のコードは別ブランチか、明示的に「spike」と分かる形で残す。** 検証用コードが本実装に紛れ込まないようにするため。
- CI(GitHub Actions): 型チェック + Biome + Vitest を必須にする。

## この順序を選んだ理由

「UIから作る」「機能単位で縦に切る」といった進め方もあるが、今回は以下の理由でドメイン先行とした。

1. **正しさの核が明確に分離できている** — FR-7.5により、ドメインは既にUIから独立している必要がある。ならば独立して作れる。
2. **要件が既にテストケースの粒度まで具体化されている** — 再接続ルールもReady判定も、書くべきテストが確定済み。この状態でTDDを使わないのはもったいない。
3. **技術リスクとロジックリスクを分離できる** — Phase 0 で技術リスクを、Phase 1 でロジックリスクを、それぞれ独立に潰せる。同時に扱うと原因の切り分けが難しくなる。
