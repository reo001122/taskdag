# 設計判断の記録

各設計文書には「なぜそうしたか」が書かれている。この文書はその裏側 ——
**何を却下したか**と、**その決定で何を失ったか** —— をまとめる。

利点だけを読むと、どの判断も自明に見える。実際にはどれも何かを引き換えにしている。
後から「ここはこうすべきでは」と考えたとき、**既に検討して捨てた案なのか、まだ誰も
考えていない案なのか**を見分けられるようにするためのもの。

書式は ADR に近いが、1決定1ファイルには分けていない。決定どうしが互いに依存しており、
並べて読めたほうが筋を追いやすいため。

---

## D-1. Project は領域であり、タグではない

**採用**: Project はキャンバス上の矩形。所属は Task が矩形の中にあるかで導出し、保存しない。

**却下した案**: Task が `project_id` を持つタグ方式。

当初はタグとして実装した(マイグレーション v1)。UI を作る過程で、意図と違うことが判明して
作り直している(v2)。枠は「同じタグを持つ Task の可視化」ではなく、**枠そのものが Project**
であり、所属は置いた場所の結果である、という理解が正しかった。

**失ったもの**

- **Task を枠の外へ一時退避させると、所属も消える。** 「今は別の場所に置いておきたいが、
  この Project の一部ではある」が表現できない。
- **1つの Task は高々1つの Project にしか属せない。** 空間上の1点は1箇所にしか置けないため、
  構造的にそうなる。複数の軸で分類したい場合は表現できない。
- 含有判定は Task の**左上の点**で行う。中心点のほうが直感に近いが、それには描画サイズが
  必要で、サイズは表示側の都合であってデータが持つべきものではない。結果として、枠の端に
  置いた Task は見た目と所属が食い違うことがある。

**得たもの**

- 位置とラベルが食い違う状態が**表現不可能**になる。保存していたら必ず起きるずれが、
  原理的に発生しない。
- 枠に入れる/出すという操作だけで所属が変わる。タグを選ぶ UI が要らない。

**この決定で発生した副作用**

整列(FR-6)が所属を壊すようになった。Task だけ並べ替えると枠から出てしまうため、
整列は枠の矩形も一緒に置き直す必要がある。実際に一度壊している。

**別案として残っているもの**: 複数軸の分類が必要になった場合、位置に依存しない
**タグ**を Project とは別概念として足す余地がある。両者は代替ではない ——
含有は「これは何の仕事の一部か」、タグは「どう切り分けて見たいか」に答えるもの。

## D-2. 導出値は保存しない(Ready/Blocked、Project 所属)

**採用**: 依存グラフと軸bから毎回計算する。DB に列を持たない。

**却下した案**: 計算結果を保存し、変更時に更新する。

**失ったもの**

- 参照のたびに計算が走る。規模(数十〜百 Task)では問題にならないが、
  桁が変われば見直しが要る。
- **SQL 側にも同じ導出を書く必要がある**(`task_readiness`、`task_project` ビュー)。
  ドメイン関数との二重実装であり、片方だけ変更すると齟齬が出る。同じグラフを両方に
  通して一致を確認するテストで担保しているが、構造的な重複そのものは残っている。

**得たもの**

- **更新漏れによる不整合が起こりえない。** 保存する方式では、依存を張り替えたときに
  Ready の更新を忘れれば、そこから先はずっと嘘の状態になる。

## D-3. Undo はスナップショット方式

**採用**: 操作のたびにグラフ全体を控え、Undo では丸ごと差し替える。

**却下した案**: コマンドパターン。操作ごとに逆操作を持たせる。

**失ったもの**

- **メモリを食う。** グラフ全体 × 履歴50件。規模の前提では数百KB程度に収まるが、
  効率の良い方式ではない。

**得たもの**

- **逆操作の実装ミスが原理的に起こらない。** 削除+自動再接続のような複合操作の
  逆操作を正しく書くのは難しく、間違えれば状態が壊れる。丸ごと戻す方式なら
  間違えようがない。

---

## D-4. 削除時の依存エッジ再接続

**採用**: 入力・出力の片方が単数なら総当たりで再接続。両方複数なら再接続しない。

**却下した案**

- **常に総当たりで繋ぐ**: 両側が複数だと組み合わせが爆発し、ユーザーの意図とも一致しない。
- **常に再接続しない**: `A→B→C` から B を消すと A と C が切れる。ここは繋がっていてほしい。

**失ったもの**

- **両側が複数の場合、依存関係が失われる。** `A1→B, A2→B, B→C1, B→C2` から B を消すと、
  4本の依存が消えて何も残らない。これは実際に外部レビューで指摘された。
- ルールが条件によって変わるため、覚えにくい。

**得たもの / 緩和策**

- 削除前に**何が消えて何が繋ぎ直されるか**を提示する(FR-1)。ルールを覚えなくても、
  その場で結果が見える。両側複数のときは「つなぎ直しは行われません」と明示する。
- 再接続は**新たな到達可能性を作らない**ため、循環を生まない。証明は
  `domain-design.md` §3.2。削除時に循環検知が不要になる。

## D-5. AI の書き込みはアプリケーション層を経由する

**採用**: MCP 等のツール経由でのみ書き込む。DB への直接書き込みは想定しない。

**却下した案**: AI が sqlite3 CLI で直接読み書きする。当初はこちらを採用していた。

**なぜ覆したか**: 削除時の再接続・Undo への記録・循環防止は、いずれもアプリケーション層の
ロジックである。DB へ直接書けば**すべて迂回される**。当初の設計はこれらの要件と両立して
いなかった。

**失ったもの**

- **アプリが起動していないと AI は操作できない。** MCP サーバーが Electron の
  main プロセス内にあるため。独立プロセス化すれば解決するが、構成が大きく複雑になる。
- ツールを1つずつ定義する手間がかかる。生の SQL なら任意の問い合わせができた。

**得たもの**

- AI の操作にも、人間の操作と同じルールが適用される。**Undo が AI の操作にも効く。**
- AI がスキーマを知らなくてよい。内部構造を変えても AI 側の呼び出しが壊れない。

## D-6. childTask は依存グラフに参加しない

**採用**: 依存エッジはトップレベルの Task 間のみ。childTask は順序付きリストとしてのみ扱う。

**却下した案**: childTask 間にも依存を張れるようにする。

**失ったもの**

- 「Entity を直さないと Repository が書けない」のような**ブロッキングを childTask 間で
  表現できない**。表現したければ、それぞれをトップレベルの Task に分ける必要がある。
- **ユーザーの直感に反しうる。** 子タスクを並べたら、その間に矢印を引きたくなるのは自然。

**得たもの**

- 「分解」と「順序」が混ざらない。childTask は見やすく整理するための構造、依存エッジは
  ブロッキングを表すもの、と役割が分かれる。
- グラフの複雑さが増えない。childTask も参加すると、ノード数が一桁増える。

**未検証の仮説**: この役割分担が実際に理解されるかは分かっていない。使ってみて直感に
反することが判明した場合、モデルの見直し対象になる。

## D-7. 配置は手動が基本、整列は明示操作のときだけ

**採用**: ユーザーが置いた座標を常に保つ。整列ボタンを押したときだけ再配置する。

**却下した案**: 依存関係から常に自動整列する。

**失ったもの**

- **ノードが増えると散らかる。** 自動整列なら常に整った状態が保たれる。
- 新規作成時の配置を決める必要がある(現在は少しずつずらして置いている)。

**得たもの**

- ユーザーが意味を持たせて置いた位置を、システムが勝手に崩さない。設計原則2に対応する。
- 空間的な記憶が働く。「あれは右下に置いた」が成立する。

---

## D-8. SQLite を採用し、平易なファイル形式を採らない

**採用**: SQLite(`node:sqlite`)。

**却下した案**: Markdown / JSON などのテキストファイル。

当初は「AI が専用の層なしに読み書きできる」ことを重視して平易なファイルを検討していた。
AI が CRUD の主体になる運用が前提だと分かった時点で、SQLite に寄せている。

**失ったもの**

- **人間が中身を直接読めない。** テキストなら任意のエディタで開ける。
- **git で差分が取れない。** バイナリのため、変更履歴を追う手段がない。
- (当初の目的だった)AI が直接読み書きすることは、結局 D-5 で禁じている。

**得たもの**

- 削除+再接続のような複合操作をトランザクションとして原子的に扱える。
- 外部キー制約で参照整合性を担保できる。ただし**循環依存の防止は SQL では表現できない**
  (グラフ探索が必要)ため、そこはアプリケーション層のみが防波堤になる。

---

## D-9. `node:sqlite` を採用し、better-sqlite3 を捨てた

**採用**: Node 標準の `node:sqlite`。Node 24 以上を要求する。

**却下した案**: better-sqlite3(当初はこちらだった)。

**なぜ覆したか**: better-sqlite3 は Electron の ABI 向けにビルドされるため、
**素の Node から読み込めない**。Vitest で永続化層のテストが1つも書けないことが、
Phase 2 の着手時に判明した。Phase 0 では Electron 内でしか検証しておらず、
顕在化していなかった。

**失ったもの**

- **開発環境に Node 24 以上を要求する。** `.nvmrc` と `engines` で明示しているが、
  古い Node しかない環境では動かない。

**得たもの**

- ネイティブモジュールの再ビルドが不要。Electron を更新するたびの手当ても、CI での
  手順も消えた。
- **テストと本番が同じ SQLite 実装で動く。** Electron 内蔵の Node と揃うため。

## D-10. 状態は2軸で、1本の遷移にしない

**採用**: 軸a(Ready/Blocked、計算)と軸b(Not Done/In Progress/Done、申告)を独立させる。

**却下した案**: `Not Started → Ready → In Progress → Blocked → Done` の単一の状態遷移。

**失ったもの**

- 状態が2つあるため、UI で両方を示す必要がある。1本なら1つのラベルで済んだ。
- 「Blocked かつ Done」という、一見おかしな状態が成立する。

**得たもの**

- **「Blocked だが着手中」が表現できる。** 先行タスクが終わる前に下準備を始めるのは
  実際に起きることで、1本の遷移では表現できない。
- 導出される状態が、ユーザーの申告を制限しない。設計原則2に対応する。

**この決定で見つかった欠陥**: UI で枠線を「着手中」に使っていたため、着手した瞬間に
Ready/Blocked が読めなくなっていた。枠線を軸a専用にして解決している。
**2軸に分けたことで表現できるようになった状態が、表示できていなかった**という形の欠陥で、
1本の遷移なら起きなかった。

## 却下した案の一覧(理由は上記の各項へ)

| 案 | 却下した理由 | 参照 |

| Project をタグとして持つ | 位置とラベルが食い違いうる | D-1 |
| Ready/Blocked を保存する | 更新漏れによる不整合が必ず起きる | D-2 |
| Undo をコマンドパターンで | 逆操作の実装ミスが状態を壊す | D-3 |
| 削除時に常に総当たりで再接続 | 組み合わせが爆発し意図と合わない | D-4 |
| AI が DB へ直接書き込む | ドメインのルールが全て迂回される | D-5 |
| childTask 間にも依存を張る | 「分解」と「順序」が混ざる | D-6 |
| 常時自動整列 | ユーザーが置いた位置を崩す | D-7 |
| Markdown / JSON で保存 | トランザクションと制約が使えない | D-8 |
| better-sqlite3 | 素の Node から読めずテストが書けない | D-9 |
| 単一の状態遷移 | 「Blocked だが着手中」が表現できない | D-10 |
