# PRD v1

ステータス: 初稿。`vision/vision.md` と、その後の設計議論を土台に作成。MVPスコープはユーザー確認済み。

## 概要

1人のエンジニアが、日々の実装作業(チケットより下の粒度)を、自ら直接編集するグラフとして表現するための、ローカル完結型ツール。ステータス信号(Ready/Blocked)はグラフから計算される。それ以外の信号(ボトルネック、全体フロー)は計算するのではなく、優れた可視化によって見えるようにすることを狙う。問題認識・設計原則の全体像は `vision/vision.md` を参照。

## ゴール

- ユーザーが実際の細かい作業(チケット未満の粒度)をグラフとして表現できる。ツール側が固定の分解粒度を強制しない。
- Ready/Blockedが常に正しく、手動でのメンテナンスを必要としない。
- グラフが成長しても可読性・操作性を保つ。これは副次的な関心事ではなく、主要な成功基準として扱う(Vision内「可視化の精度は付随的な実装詳細ではない」を参照)。
- データは完全にローカルに保持され、AIコーディングツールが摩擦なく読み書きできる構造になっている。

## 非ゴール

Visionから変更なく引き継ぎ: チーム・複数ユーザーでの調整、クラウド保存・同期、外部チケット管理システム(Jira, GitHub Issues, Linear等)との連携、プロダクトがユーザーに代わってタスクを実行すること、分解粒度の強制。

## ユーザー

個人のエンジニア1名(会社員または個人開発者)。チームや権限といった概念は存在しない。

## コア概念(用語集)

- **Task**: 中核となる単位。0個以上の **childTask** を持てる(深さは1に限定 — childTaskはさらに自分の子を持てない)。
- **依存エッジ(Dependency edge)**: トップレベルのTask同士のみを接続する(childTaskは対象外)。2種類ある: **厳密(strict)**(BはAがDoneになるまで開始できない)と **緩やか(loose)**(自然な順序だが強制力はない)。
- **Project**: コンテナではなくタグ。トップレベルのTaskは0個または1個のProjectタグを持つ。childTaskは常に親のタグを継承する。
- **軸a(計算される)**: Ready / Blocked。厳密な依存エッジから導出される。トップレベルのTaskに対して定義される。childTaskについては未決定(Open Questions参照)。
- **軸b(自己申告)**: Not Done / In Progress / Done。実際に作業した主体(人間またはAI)が設定する。軸aとは独立している。

## 機能要件

### 1. タスクグラフの構造
- 1.1 Taskの作成・編集・削除。
- 1.2 Task配下のchildTaskの追加・削除(深さは1に限定。childTaskはさらに子を持てない)。
- 1.3 トップレベルのTask同士の間で、依存エッジ(厳密 or 緩やか)を作成・削除できる。
- 1.4 childTaskに対する依存エッジの作成は不可(規約ではなく、仕組みとして禁止する)。
- 1.5 依存エッジはProjectタグを跨いでよい(「AAA」タグのTaskが「BBB」タグ、または無タグのTaskに依存してもよい)。

### 2. Projectタグ
- 2.1 トップレベルのTaskに0個または1個のProjectタグを付与できる。
- 2.2 childTaskは親のProjectタグを自動的に継承する。個別には設定できない。
- 2.3 TaskをProjectの視覚的な領域にドラッグすると、そのタグが自動的に付与される(Interaction Expectations参照)。

### 3. 状態管理
- 3.1 トップレベルのTaskについて、軸a(Ready/Blocked)を、入力される厳密な依存エッジのみから計算する(緩やかな依存エッジは軸aに一切影響しない)。
- 3.2 作業主体(人間、またはユーザーに代わって作業するAI)が、任意のTask・childTaskに対して軸b(Not Done → In Progress → Done)を設定できる。
- 3.3 軸aはTaskの編集や軸bの設定を制限してはならない。Blockedはあくまで情報表示である。
- 3.4 親Taskの軸bと、そのchildTaskたちの軸bは、双方向に自動連動しない(独立を維持する)。

### 4. 可視化
- 4.1 全てのTaskとProjectは単一の共有キャンバス上に描画される(プロジェクトごとの個別画面は持たない)。
- 4.2 childTaskを持つTaskは、折りたたみ・展開ができる(自身の子を畳む)。
- 4.3 Projectに属するTask群は、クラスタとして折りたたみ・展開ができる。折りたたまれている間、対象Taskへの・からのエッジは、折りたたまれたクラスタの形状へ接続されているように描画される(あくまで表示上の再描画であり、データ上のエッジは引き続き特定のTaskを参照している)。
- 4.4 実運用に近い規模でのグラフの可読性・操作性は、この機能領域における一次的な合格基準であり、後回しにできる磨き込みではない。

### 5. AI連携
- 5.1 基本的な操作(Taskの追加・削除、軸bの設定、軸aの参照)について、専用のAPI層を必要とせず、AIコーディングツールがデータを直接読み書きできるような構造にする。
- 5.2 主体が誰であっても、プロダクト自体がTaskの記述する作業を実行することはない。

### 6. データ・保存
- 6.1 全データはローカルに保存される。コア機能はネットワーク・クラウドに依存しない。
- 6.2 外部チケット管理システムとの連携は行わない。

## 操作面の期待事項(実装を縛るものではないが、意図は縛るもの)

構造上の3つの操作 — Taskを子タスク化する、2つのTaskを依存エッジで接続する、Projectタグを付与する — は、それぞれシンプルで直接的なマウス操作で到達できるようにする(例: ドラッグでタグ付け)。「フラット+エッジ接続」と「子タスクとして入れ子」の間の組み替えは、一方向のコミットメントではなく、流動的に行える感覚にする。具体的な操作(インタラクション)設計自体は、本ドキュメントのスコープ外とする。

## Open Questions(未解決。MVP定義をブロックはしないが、要件定義・設計フェーズまでに解決すべき)

- 軸aをchildTaskが親から継承すべきか、それともchildTaskについては未定義のままにするか。
- 厳密な依存は常に技術的・構造的な制約に紐づくものか、それとも純粋にワークフロー由来の厳密な依存も存在するか。
- 依存の種類が2つ(厳密/緩やか)で十分か、それともさらに段階が必要か。
- 「AI連携」(5.1)について、専用の機能(組み込みのチャット/インターフェース等)が本当に必要か、それとも十分に平易でローカルなファイル形式(Claude Codeのような汎用AIコーディングツールが、プロダクト側の独自の連携機構なしにそのまま読み書きできるもの)であれば足りるのか。
  - **判明した点**: この答えは保存形式(ストレージ)の技術選定に従属する。マークダウン/JSONのような平易なファイルであれば、ファイル形式自体がそのままAI連携要件を満たせる可能性が高い。一方、SQLiteのようなDBを採用する場合は、部分的な取得・更新のためにAPI層を別途用意した方がよいと考えられる。
  - **扱い**: 保存形式そのものの選定はPRDでは決めず、要件定義・設計フェーズで行う。ただしその選定の際は「AIが専用API層なしに読み書きできるか」を判断基準の一つとして明示的に持ち込むこと。

## Parking Lot(明示的に対象外としたもの。本PRDのスコープ外)

- In Progressに入ったことを契機とする、進捗メモ・日記的なログ。
- 期限・工数ベースの完了率(親単位、Project単位、任意で工数による重み付け)。

## MVPスコープ(確認済み)

方針: 未検証の細部にコミットすることなく、この製品の本当の賭け(自ら編集するグラフ + 計算されるReady/Blocked + 可読な可視化)を検証できる最小構成。

**MVPに含める:**
- Task + childTask(1.1, 1.2)、依存エッジは厳密なもののみ(1.3の厳密なケース, 1.4, 1.5)
- Projectタグ付け(2.1, 2.2) — タグに基づく折りたたみ(4.3)は後回しでよいと思われるが、タグの付与自体は実装コストが低くモデル検証に不可欠なため含める
- 状態モデル全体(3.1〜3.4)
- 単一キャンバス + Task単位の折りたたみ(4.1, 4.2)。Projectクラスタの折りたたみ(4.3)は、エッジ再描画の複雑さを踏まえるとPhase 2の有力候補
- 平易で可読なファイル形式によるローカル保存(6.1, 6.2) — これだけで、専用のAI機能なしに5.1を満たせる可能性がある(上記Open Question参照)

**Phase 2以降に先送り:**
- 緩やか(非ブロッキング)な依存エッジ — あくまで情報表示用であり、Ready/Blockedというコアの仕組みには不要。厳密な依存のみの版が検証された後に追加すれば安全
- エッジ再描画を伴うProjectクラスタの折りたたみ(4.3)
- 「ファイルが十分平易で直接読み書きできる」という結論になった場合、それを超える専用のAI向け機能(上記Open Question次第)
- Parking Lotの全項目

上記のスコープはユーザー確認済み。
