# ドメイン文書

コードベースを調べる際、Engineering 系 Skill がこのリポジトリのドメイン文書をどう読むか。

**このリポジトリは `CONTEXT.md` や `docs/adr/` を使わない。** 過去に一度、仕様を述べる
文書が複数並んで互いに食い違う、という同じ形の問題を踏んでいる(`CLAUDE.md` §2「仕様を
述べる文書を増やさない」を参照)。その分割を再現しない。以下の既存文書を読むこと。

## 調査の前に読むもの

- **`requirements.md`** — 唯一の規範文書。何がどう振る舞うべきか、受け入れ条件つき。
  他の文書がこれと食い違ったら、他の文書が古い。
- **`README.md`** — プロジェクトの背景とスコープ(意図的にやらないことを含む)。
- **`design/*.md`** — どう作られているか。
- **`design/decisions.md`** — このリポジトリでの ADR に相当する。`D-1`, `D-2`, ... と
  番号が振られ、各項目に「何を却下したか」「何を犠牲にしたか」が書かれている。

いずれかが存在しなくても**黙って進める**。存在しないことを指摘したり、代わりに
`CONTEXT.md` や `docs/adr/` を作ることを提案しない。

## ファイル構成

単一コンテキストのリポジトリ(このリポジトリは単一コンテキスト):

```
/
├── requirements.md
├── README.md
├── design/
│   ├── decisions.md      ← D-1, D-2, ... 新しい判断はここに追記する
│   ├── coding-standards.md
│   └── ...
└── src/
```

## 用語は `requirements.md` に合わせる

出力(issue のタイトル、リファクタ提案、仮説、テスト名)でドメインの概念に言及するときは、
`requirements.md` で定義された用語を使う。同義語に流れない。

必要な概念が `requirements.md` に無い場合、それは何かのサインである。このプロジェクトが
使わない言葉を作ろうとしている(考え直す)か、実際に語彙の欠落がある(別の用語集ファイルを
作る理由ではなく、メンテナに提起する理由)かのいずれか。

## `design/decisions.md` との矛盾を明示する

出力が既存の項目と矛盾する場合、黙って上書きせず明示する。

> _D-2(Ready/Blocked を保存せず導出する)と矛盾するが、次の理由で再検討の価値がある…_

新しい設計判断は、新しい ADR ファイルを作るのではなく、`design/decisions.md` に
新しい `D-<n>` 項目(何を却下したか、何を犠牲にしたか)として**追記する**。
